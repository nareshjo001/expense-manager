# ML-001-T02: Deduplication and label-ambiguity quantification

Quantifies two independent data-quality issues in
`ml-service/usedDatasets/merged_expenses.csv` (97,056 rows -- see
[ML-001-T01](ML-001-dataset-provenance-and-taxonomy.md) for its
provenance and the `expenseName`/`expenseCategory` -> canonical-category
mapping this analysis reuses), so ML-001-T03 (grouped train/val/test
splitting) starts from a dataset whose real distinct-example count and
label noise are both known quantities rather than assumed.

Reproducible via `ml-service/training/analyze_dataset_ambiguity.py`
(new script, this task). Findings below are that script's output against
the current dataset on 2026-09-03.

## 1. Exact-duplicate rows

| Metric | Value |
|---|---|
| Total rows | 97,056 |
| Rows that are part of an exact `(expenseName, expenseCategory)` duplicate group | 86,222 (88.8%) |
| Distinct `(expenseName, expenseCategory)` pairs | 11,514 |
| Rows removable by collapsing each group to one copy | **74,708 (77.0%)** |

**This is the dominant finding.** Only 11,514 of the 97,056 rows (11.9%)
are actually distinct training examples; the rest are exact repeats of
one of those 11,514 pairs. This matches what
[ML-001-T01](ML-001-dataset-provenance-and-taxonomy.md) already flagged
as an open provenance gap for `used_app_data.csv` and
`merchant_dataset_generated.csv`: at least one of the five source files
was very likely generated by templating a smaller set of
merchant/category pairs at high volume, not collected as 97k independent
observations.

**Why this matters for ML-001-T03 (grouped splitting):** a random
train/test split over the *raw* 97,056 rows would put many exact copies
of the same 11,514 underlying examples on both sides of the split. That
inflates measured test accuracy without the model having generalized to
anything new -- the real distinct-example count this dataset offers is
11,514, not 97,056, and T03's grouping key must dedupe (or group by the
underlying pair) before splitting, not just group by description.

## 2. Label ambiguity: does the same description ever carry more than one category?

Computed on `normalize_expense_name()`'s grouping key from
`training/category_config.py`, which is deliberately case-preserving
(it already backs production dedup/conflict-grouping keys elsewhere, not
just this analysis -- see that function's docstring). Reported two ways
since case sensitivity changes the picture materially:

| | Case-preserving (production key, as-is) | Case-insensitive (upper bound) |
|---|---|---|
| Ambiguous normalized names | 18 | 22 |
| Rows affected | 933 | 1,619 |
| % of usable rows | 0.96% | 1.67% |

`unmapped_category_rows` and `empty_name_rows` are both **0** -- every
row's raw category string maps to a canonical category via
`CATEGORY_ALIASES`, and every row has a non-empty name. The taxonomy
mapping T01 documented is complete against this dataset; ambiguity here
is a genuine same-description-different-category issue, not a mapping
gap.

The case-preserving vs. case-insensitive gap is itself informative: three
of the case-preserving "ambiguous" groups (`perfume`, `PERFUME`,
`Perfume`, 196+158+154 = 508 rows) are the *same* real ambiguity split
across case variants of one word, plus `train ticket` and `ola cab` only
surface as ambiguous once case is folded. Since production's own
dedup/grouping key is case-preserving, production likely already treats
these as separate keys too -- worth a follow-up check outside this task's
scope, since it would mean production dedup logic undercounts duplicates
of the same real-world merchant string for the same reason.

### Top ambiguous descriptions (case-insensitive), by row count

| Description | Categories it appears under | Rows | Read |
|---|---|---|---|
| `perfume` (+ case/prefix variants: `gpay perfume`, `perfume txn`, `paytm perfume`, etc.) | Personal Care, Shopping | ~600 combined | Genuinely ambiguous purchase type -- a perfume is plausibly either a personal-care item or a general shopping purchase; no data error, a real labeling judgment call the source data made inconsistently. |
| `bus ticket` | Transport, Travel | 260 | Genuinely ambiguous -- a bus fare is a routine Transport expense for a commute, or a Travel expense for a trip, and the description alone cannot disambiguate which. |
| `shampoo`, `soap` | Groceries, Personal Care | 229, 225 | Same pattern as perfume -- toiletries plausibly belong to either category depending on where the source labeler drew the line. |
| `train ticket` | Transport, Travel | 165 | Same ambiguity as `bus ticket`. |
| `ola cab` | Transport, Travel | 90 | Ride-hailing fare -- same commute-vs-trip ambiguity. |
| `cycle cover`, `laptop stand`, `keyboard`, `instamart` | Others / Shopping / Groceries (small counts) | <=5 each | Low-volume, likely one-off inconsistent labeling rather than a systematic category boundary issue. |

The pattern is consistent: ambiguity concentrates in a small number of
genuinely dual-purpose item/description categories (personal-care vs.
shopping toiletries, transport vs. travel fares), not random noise spread
across the dataset. 1.67% of rows is a small fraction, but it is
concentrated exactly where a model's confusion matrix would also be
expected to show the most category-pair confusion, which makes it a
useful thing to cross-check once ML-001-T05 (confusion matrix) exists.

## Recommendation for ML-001-T03

1. **Deduplicate to unique `(expenseName, expenseCategory)` pairs (11,514
   rows) before grouped splitting**, or at minimum use the pair itself
   (not just the description) as the grouping key so exact duplicates of
   the same pair cannot land on both sides of a split. This is the
   higher-value fix of the two findings here given it affects 77% of rows
   versus ambiguity's 1.67%.
2. **Do not silently drop the ~933-1,619 ambiguous rows.** They are a
   real, small, concentrated source of label noise (a handful of
   genuinely dual-category items), not a bug to delete. Options for T03
   to weigh: leave them in and accept a small ceiling on achievable
   accuracy for those specific descriptions, resolve each ambiguous
   description to its majority category as a documented, reviewable
   decision, or route them to a held-out "known-ambiguous" evaluation
   slice so the model's performance on genuinely hard cases is measured
   separately from its performance on clean-label data. This task
   quantifies the problem; choosing among those options belongs to T03
   (splitting strategy) and T06 (promotion gates), not here.
